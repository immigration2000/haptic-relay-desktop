# Haptic Relay 빠른 시연 기능 설계

## 목표

하드웨어가 없는 환경에서도 스트리머와 시청자 사이의 모션 전송을 명확하게 시연할 수 있도록 다음 기능을 순서대로 추가한다.

1. 자동 패턴 생성
2. 수동 동작 녹화 및 반복 재생
3. 시청자별 네트워크 품질 진단

각 단계는 테스트 가능한 완성 상태로 끝내고 별도의 Windows EXE를 배포한다. 모든 모션 소스는 기존 `DemoMotionStream -> MotionFrame -> RelayClient -> relay server` 경로를 사용한다. 시연용 기능이 실제 릴레이 동작을 우회하는 별도 가짜 데이터 경로를 만들지 않는다.

## 조사 결과

- [MultiFunPlayer](https://github.com/Yoooi0/MultiFunPlayer)는 사인, 삼각, 바운스, 톱니, 사각 패턴과 범위·속도 조절을 제공한다. 반복 시연에는 자동 패턴과 실시간 미리보기가 가장 직접적이다.
- [Buttplug 출력 명세](https://buttplug.io/docs/spec/output/)는 빠른 위치 갱신과 목표 위치까지의 지속시간을 분리한다. 현재 `MotionFrame.durationMs`를 유지하면 향후 보간과 장비 출력에 연결할 수 있다.
- [Intiface Central](https://intiface.com/docs/intiface-central/ui/app-modes-engine-control-panel/)은 장비가 없어도 시뮬레이션 장비와 출력 상태를 보여준다. 이번 앱에서는 수신 모니터와 진단 수치가 이 검증 역할을 담당한다.
- [The Handy API v2](https://handyfeeling.com/api/handy/v2/docs/)는 왕복시간과 시간 동기화를 별도 기능으로 다룬다. 동기화되지 않은 두 PC의 시계로 편도 지연을 계산하지 않고, 서버 왕복시간을 명시적으로 측정한다.

## 검토한 구현 방식

### 선택: 단계별 수직 구현

자동 패턴, 녹화·반복, 네트워크 진단을 각각 UI부터 릴레이 검증과 설치 파일까지 완성한다. 첫 시연판을 가장 빨리 확보하면서 단계별 회귀 원인을 좁힐 수 있다.

### 기각: 세 기능을 한 번에 배포

설치 파일 수는 줄지만, 녹화 상태와 진단 프로토콜 문제가 자동 패턴 검증까지 막을 수 있다. 빠른 시연 목표와 맞지 않는다.

### 기각: 범용 모션 엔진을 먼저 전면 재작성

장기적으로는 확장성이 높지만 현재 수동 30Hz 스트림을 크게 바꾸게 된다. 이번 범위에서는 필요한 경계만 분리하고 범용 타임라인 편집기나 스크립트 엔진은 만들지 않는다.

## 공통 아키텍처

### 프로세스 책임

- Renderer: 모드 선택, 설정 입력, 그래프와 상태 표시만 담당한다.
- Electron main: 30Hz 시간 기준, 패턴 생성, 녹화, 재생, 입력 검증과 안전 정지를 담당한다.
- `RelayClient`: 최신 프레임 우선 전송, 시퀀스 추적, 진단 측정을 담당한다.
- Relay server: 모션 전달과 검증된 진단 메시지 전달만 담당한다. 진단 기록을 영구 저장하지 않는다.

Renderer 타이머는 창이 가려지거나 최소화될 때 제한될 수 있으므로 모션 생성과 재생 시간 기준으로 사용하지 않는다.

### 모션 엔진 경계

기존 `DemoMotionStream`은 다음 상태를 명시적으로 관리하는 메인 프로세스 서비스로 확장한다.

```text
idle -> manual -> idle
idle -> pattern -> idle
idle -> recording -> recorded
recorded -> playback -> recorded
any active state -> emergency stop -> idle
```

엔진은 매 틱마다 `{ intensity, position, timestamp, durationMs }`를 기존 publish 콜백에 전달한다. 패턴 계산과 녹화 재생 계산은 별도의 순수 모듈로 분리해 가짜 시계로 테스트할 수 있게 한다. 상태 전환은 IPC invoke로 처리하고, 30Hz 중간 값 갱신처럼 응답이 필요 없는 수동 입력만 기존 IPC send 방식을 유지한다.

### 공통 안전 규칙

- 위치와 강도는 Electron main과 relay server 양쪽에서 `0..1`로 제한한다.
- 자동 패턴 시작 시 현재 위치에서 첫 패턴 위치까지 300ms 동안 선형 진입한다.
- 일반 정지는 마지막 위치를 유지한 채 강도 0 프레임을 한 번 보낸다.
- 긴급 정지, 방 퇴장, 연결 해제, 앱 종료는 패턴·녹화·재생 타이머와 대기 프레임을 모두 비운다.
- 기존 하드웨어 보호 설정의 강도와 위치 범위 제한은 각 앱의 로컬 장비 출력 단계에서 모든 모션 소스에 동일하게 적용한다. 네트워크 원본 프레임은 공통 `0..1` 제한만 적용한다.
- 한 번에 하나의 모션 소스만 활성화한다. 다른 모드 시작 요청은 현재 모드를 안전 정지한 뒤 전환한다.

## 1단계: 자동 패턴

### 기능

- 모드: 수동, 자동 패턴
- 패턴: 사인, 삼각, 펄스, 톱니
- 설정: 주기 `500..5000ms`, 최소·최대 위치 `0..1`, 강도 `0..1`
- 최소 위치는 최대 위치보다 클 수 없다.
- UI는 현재 위치, 강도, 패턴 진행 상태를 그래프로 표시한다.

패턴 위상은 monotonic clock의 경과 시간으로 계산하고 프레임 timestamp는 `Date.now()`로 기록한다. 타이머가 잠시 늦어져도 틱 횟수를 누적하지 않고 현재 경과 시간의 위치를 계산해 밀린 프레임을 연속 발행하지 않는다. 펄스 패턴은 주기의 10%를 전환 구간으로 사용해 최소·최대 위치 사이를 순간 이동하지 않으며, 시작 시 300ms 안전 진입도 항상 적용한다.

### 데이터 흐름

```text
Host UI pattern config
  -> validated IPC
  -> pattern calculator at 30Hz
  -> DemoMotionStream publish callback
  -> hardware protection + RelayClient
  -> binary MotionFrame V2
  -> viewers
```

### 배포 기준

- 버전: `v0.1.1-demo.3`
- 수동 모드 회귀 없음
- 네 패턴이 30Hz 최신 프레임 정책을 통해 두 번째 클라이언트에 전달됨
- 정지와 긴급 정지 후 추가 모션 프레임이 발생하지 않음

## 2단계: 동작 녹화 및 반복

### 기능

- 수동 시연의 실제 출력 위치와 강도를 30Hz로 녹화한다.
- 최대 길이는 30초이며 최대 약 900개 샘플이다.
- 샘플 형식은 `{ offsetMs, intensity, position }`이다.
- 녹화가 30초에 도달하면 자동 종료하고 재생 가능한 상태로 전환한다.
- 재생 속도는 `0.5x`, `1x`, `1.5x`, `2x`다.
- 반복 재생을 켜거나 끌 수 있고, 반복을 끈 재생은 마지막 샘플 뒤 안전 정지한다.
- 데이터는 현재 앱 실행 중 메모리에만 유지한다.

재생은 타이머 틱 번호가 아니라 재생 시작 후 경과 시간으로 샘플 위치를 찾는다. 인접 샘플 사이를 선형 보간해 타이머 지터나 배속 재생에서도 급격한 계단 현상을 줄인다. 재생 결과도 일반 30Hz publish 콜백을 사용하므로 별도 네트워크 경로가 없다.

### 수명 주기

- 새 녹화를 시작하면 이전 녹화는 지운다.
- 샘플이 두 개 미만이면 재생을 거부하고 UI에 이유를 표시한다.
- 녹화 중 방 연결이 끊기면 녹화를 종료하고 미완성 데이터는 폐기한다.
- 방 퇴장, 긴급 정지, 앱 종료 시 재생을 중단한다.
- 파일 저장, 불러오기, 편집, funscript 변환은 이번 단계에 포함하지 않는다.

### 배포 기준

- 버전: `v0.1.1-demo.4`
- 30초 제한, 네 배속, 단일 재생과 반복 재생이 결정적인 가짜 시계 테스트를 통과함
- 재생 프레임이 두 번째 클라이언트 수신 모니터에 표시됨
- 중단 조건 이후 재생 프레임이 남지 않음

## 3단계: 네트워크 진단

### 측정 항목

- 서버 왕복시간(RTT): Socket.IO ack 기반 probe의 송수신 경과 시간
- 수신 Hz: 최근 5초 동안 승인된 모션 프레임 수
- 수신 간격 변동: 최근 5초 프레임 도착 간격의 평균 절대 편차
- 손실률: 최근 5초의 `lost / (accepted + lost)`
- 중복과 역순 프레임: 기존 `MotionSequenceTracker` 카운터의 최근 5초 증분

스트리머와 시청자 PC 시계가 동기화됐다는 보장이 없으므로 `sourceTimeMs`로 편도 네트워크 지연을 표시하지 않는다. 모션이 2초 이상 전송되지 않으면 품질을 나쁨으로 판정하지 않고 `대기` 상태를 표시한다.

### 상태 판정

- 정상: RTT 200ms 미만, 수신 24Hz 이상, 간격 변동 20ms 미만, 손실률 1% 미만
- 주의: RTT 500ms 미만, 수신 15Hz 이상, 간격 변동 50ms 미만, 손실률 5% 미만
- 불안정: 위 주의 기준 중 하나 이상을 벗어남
- 대기: 최근 2초간 모션 프레임 없음
- 측정 불가: 구형 서버 또는 probe 실패로 RTT를 얻을 수 없음

수신 Hz는 서버의 실제 전송 상한 설정에 따라 정상 기준을 조정한다. 초기 Node 릴레이의 기본 30Hz에서는 위 기준을 사용한다.

### 진단 프로토콜

```text
Viewer -> diagnostics:probe -> Relay ack
Viewer local 5s window -> diagnostics:report every 2s
Relay validates attached viewer and numeric bounds
Relay -> host socket only -> diagnostics:viewer
Host main process map -> renderer batch update once per second
```

클라이언트 보고 주기는 2초이며 시작 시 `0..500ms` 임의 지연을 둬 500명이 동시에 접속해도 보고가 한 시점에 몰리지 않게 한다. 서버는 소켓별 진단 보고를 초당 1회로 제한하고, payload의 room 또는 socket 식별자는 신뢰하지 않고 서버 세션에서 다시 채운다. 호스트 앱은 보고 이벤트마다 renderer를 갱신하지 않고 메모리 맵에 모아 1초마다 한 번 전달한다.

보고당 200바이트 이하를 목표로 하면 500명 방의 진단 본문은 한 방향 약 50KB/s다. 프로토콜 오버헤드를 포함해도 모션 fanout보다 작은 운영 보조 트래픽으로 제한한다.

구형 서버가 진단 이벤트를 지원하지 않으면 probe를 반복해서 실패시키지 않는다. 해당 연결에서는 RTT와 호스트의 시청자별 품질을 `측정 불가`로 두고, 시청자 로컬의 수신 Hz·간격 변동·시퀀스 통계는 계속 표시한다.

### 배포 기준

- 버전: `v0.1.1-demo.5`
- 서버와 EXE를 함께 배포한다.
- 시청자 로컬 진단과 스트리머의 시청자별 상태가 일치한다.
- 손실, 중복, 역순, 지터, 무전송 상태를 합성한 테스트를 통과한다.
- 500개 모의 시청자 진단 보고에서 서버 rate limit과 호스트 renderer batching이 유지된다.

## 오류 처리

- IPC 입력이 범위나 형식 검증에 실패하면 현재 모션 상태를 바꾸지 않고 명시적 오류 코드를 반환한다.
- 패턴·재생 타이머 내부 오류는 타이머를 중단하고 강도 0 프레임을 보낸 뒤 로그에 기록한다.
- 녹화 한도 도달은 오류가 아니라 정상 자동 종료 상태다.
- 진단 메시지는 모션과 분리한다. 진단 실패가 모션 수신, 하드웨어 큐 또는 긴급 정지를 막지 않는다.
- 구형 서버, 일시적인 probe timeout, 누락된 시청자 보고는 연결 오류 팝업 대신 해당 진단 항목의 상태로 표시한다.
- 창이 닫힌 뒤 Electron 이벤트가 renderer로 전달되지 않도록 기존 `mainWindow.isDestroyed()` 보호를 모든 새 push 이벤트에 적용한다.

## UI 배치

- 스트리머 `실시간 시연` 패널에 `수동 / 자동 패턴 / 녹화 재생` 세그먼트 제어를 둔다.
- 자동 패턴은 패턴 선택, 속도, 최소·최대 위치, 강도, 시작·정지를 한 패널에서 제공한다.
- 녹화 재생은 녹화 시간, 간단한 타임라인, 배속, 반복, 녹화·재생·정지 명령을 제공한다.
- 시청자 수신 모니터에는 로컬 진단 요약을 추가한다.
- 스트리머 참가자 목록에는 상태 표시를 추가하고 상세 진단은 참가자 행을 선택했을 때만 펼친다.
- 기존 1180x780 기준과 960x640 최소 창에서 가로 스크롤 없이 동작해야 한다.

## 테스트 전략

### 단위 테스트

- 네 패턴의 주요 위상 값, 범위와 주기 경계
- 300ms 안전 진입과 정지 프레임
- 녹화 30초 제한, 샘플 수, 배속별 시간 변환, 보간과 반복 경계
- 5초 진단 창, 카운터 증분, 상태 임계값과 무전송 대기 상태
- uint32 시퀀스 wraparound와 기존 중복·역순 필터 회귀

### IPC 및 서버 테스트

- 새 IPC payload 검증과 허용되지 않은 renderer 거부
- 방 퇴장·재연결·긴급 정지에서 모든 모션 상태 정리
- 진단 보고 spoofing 차단, 초당 rate limit, host 전용 라우팅
- 구형 서버에서 로컬 진단 fallback

### 통합 및 패키지 테스트

- 로컬 relay + Electron 두 인스턴스로 각 단계의 실제 송수신 확인
- 설치된 EXE 두 인스턴스 테스트를 `APP_EXECUTABLE` 경로로 실행
- 1180x780과 960x640에서 Playwright 스크린샷과 오버플로 확인
- 각 단계마다 typecheck, 전체 테스트, production build, Windows installer 생성 후 설치·삭제 확인

1. 자동 패턴 구현, 검증, 문서 업데이트, `v0.1.1-demo.3` EXE
2. 녹화·반복 구현, 검증, 문서 업데이트, `v0.1.1-demo.4` EXE
3. 네트워크 진단과 서버 업데이트, 500명 합성 검증, `v0.1.1-demo.5` EXE

각 단계는 독립 커밋들로 구성하되 릴리즈 태그는 해당 단계의 전체 검증이 끝난 커밋에만 붙인다.

## 제외 범위

- 실제 OSR/T-Code 하드웨어 연결 검증
- 랜덤 패턴
- 녹화 파일 저장, 불러오기, 편집, 공유
- funscript 가져오기 또는 내보내기
- 정확한 편도 지연과 PC 간 시계 동기화
- 진단 데이터 영구 저장과 운영 분석 대시보드
- 현재 Node 릴레이를 Go로 교체하는 작업

## 완료 조건

- 세 기능이 기존 모션 프레임 경로와 안전 제어를 사용한다.
- 하드웨어 없이 두 앱의 송신·수신 모니터로 동작을 확인할 수 있다.
- 각 단계가 자체 테스트와 설치된 EXE 통합 테스트를 통과한다.
- 단계별 설치 파일과 테스트 설명서가 GitHub Release에 함께 게시된다.
